## 1. Executive Summary

CMPDI and CIL subsidiaries are responsible for compiling geological, mining, and production data into reports used for governance, policy planning, and responses to parliamentary and administrative inquiries. Today this is a largely manual process spanning scanned PDFs, digital documents, spreadsheets, images, and historical archives — leading to slow turnaround, inconsistent quality, and heavy reliance on individual staff expertise.

This project proposes an AI-powered document processing and reporting platform that ingests heterogeneous data sources, extracts and validates structured information, and produces reports, thematic summaries, query-driven answers, and evidence-backed recommendations — reducing manual effort while improving accuracy, consistency, and traceability.

## 2. Problem Statement (As Given)

CMPDI/CIL subsidiaries play a key role in providing geological and mining information to the Ministry of Coal and responding to parliamentary and high-priority administrative inquiries. Reports require compilation of data from scanned PDFs, digital documents, spreadsheets, images, and historical archives. The current manual workflow results in:

- High dependence on individual expertise
- Delay in generating reports and analytics
- Higher probability of manual errors
- Limited ability to quickly retrieve insights when required

## 5. Core Modules (As Mandated by PS, Plus Recommendation Engine)

### Module 1: Automated Report Generation Platform

**Purpose:** Ingest data from multiple source types and auto-generate structured reports.

**Functional Requirements:**

- **FR1.1:** Accept input from scanned PDFs, born-digital PDFs, Word documents, Excel/CSV spreadsheets, images, and archived historical files
- **FR1.2:** Apply OCR/document-AI extraction on scanned PDFs and images to convert to machine-readable text and structured fields. Sub-requirements:
  - **FR1.2a (Tables):** Detect table regions and extract rows/columns into structured form using layout analysis (e.g., PaddleOCR PP-Structure), not flat text. Merged cells and multi-page tables are handled on a best-effort basis and flagged when confidence is low.
  - **FR1.2b (Languages):** Support English and Hindi (Devanagari) text recognition. Mixed-language pages are processed per region. Language is recorded per extracted field.
  - **FR1.2c (Degraded scans):** Pre-process poor scans before OCR (deskew, denoise, contrast/binarization). Pages that still fall below the OCR confidence threshold are routed to human review instead of being silently accepted.
  - **FR1.2d (Maps, plans, borehole logs, sections):** Non-text geological artifacts are stored as image assets linked to their parent document. The system extracts what is machine-readable (title block, legend text, coordinates, scale, labels, captions) and attaches it as metadata. Interpretation of the drawing itself is out of scope; reviewers can add tags manually. An optional vision-LLM captioning step may be used on public/synthetic samples only (see §7B).
- **FR1.3:** Parse born-digital documents and spreadsheets directly (no OCR needed) for higher accuracy/speed
- **FR1.4:** Extract structured entities relevant to geology/mining domain — e.g., seam data, reserve estimates, production figures, location/coordinates, dates, survey references (full entity list in §5A)
- **FR1.5:** Validate extracted data against the rules catalog in §5A (numeric ranges, mandatory fields, unit and period consistency, cross-document consistency checks)
- **FR1.6:** Auto-generate report templates populated with validated data. Minimum templates: monthly production report, geological survey summary, and parliamentary Q&A brief (see FR3.8 for the parliamentary format)
- **FR1.7:** Maintain traceability — every value in a generated report must be linkable back to its source document and page/table/cell location
- **FR1.8:** Support human-in-the-loop review/correction before final report approval
- **FR1.9:** Export generated reports in standard formats (PDF, DOCX, XLSX)
- **FR1.10 (Integration demo):** A watched-folder ingestion connector picks up files dropped into a configured directory (stand-in for an SFTP/email/shared-drive drop used by subsidiaries), runs the full pipeline, and places exported reports into an output directory using a subsidiary-style export template. This is the one working integration touchpoint in the hackathon build; SAP/ERP remains conceptual (§7A).
- **FR1.11 (Feedback capture):** Every reviewer correction (field value, unit, mapping, rejected extraction) is stored with the original value, corrected value, document type, and extractor version. This forms a labeled dataset for later extractor/rule improvement and for measuring accuracy drift.

**Non-Functional Requirements:**

- Extraction accuracy target: quantified and displayed as a percentage (measured, not assumed — see §12)
- Report generation time: quantified reduction vs. manual baseline (target defined in §15, baseline method in §12)

### Module 2: Automated Word Cloud and Topic Identification Module

**Purpose:** Surface thematic patterns and recurring topics across compiled documents.

**Functional Requirements:**

- **FR2.1:** Generate word clouds from extracted/compiled text corpora, filterable by date range, subsidiary, or document type
- **FR2.2:** Apply topic modeling to identify recurring themes across reports and archives
- **FR2.3:** Track topic trends over time (e.g., which issues are increasingly mentioned across quarters/years)
- **FR2.4:** Allow drill-down from a topic/word to the underlying source documents
- **FR2.5:** Support domain-specific stopword lists and terminology (mining/geological jargon), including Hindi stopwords, to improve topic relevance
- **FR2.6 (Small-corpus handling):** BERTopic is the primary method but needs enough text to produce stable topics. A minimum corpus size is defined at build time (initial working assumption: several hundred text chunks after splitting). Below that threshold, or when topic coherence is poor, the module falls back to TF-IDF keyword extraction and/or LDA, and the UI shows which method produced the result.

### Module 3: AI-Based Query and Response System

**Purpose:** Allow users to ask natural-language questions and receive accurate, source-grounded answers.

Parliamentary and ministry queries are mostly numeric (totals, comparisons, year-on-year change across subsidiaries). Retrieval over text chunks alone is unreliable for that, so Module 3 is a hybrid: numeric/aggregate questions are answered from the validated structured tables, narrative questions from retrieved document text.

**Functional Requirements:**

- **FR3.1:** Accept natural-language queries from users (e.g., "What was coal production in [subsidiary] in [year]?")
- **FR3.2:** Route each query to one of three paths using a query classifier: (a) **structured path** — text-to-SQL over the validated PostgreSQL tables for figures, sums, comparisons, and trends; (b) **narrative path** — retrieval-augmented generation (RAG) over the vector index for explanations, context, and qualitative questions; (c) **hybrid** — both, combined in one answer
- **FR3.3:** Generate responses grounded in retrieved source data, with citations/links to originating documents (for the structured path: the SQL used plus the source document/page of each underlying row)
- **FR3.4:** Flag low-confidence answers or insufficient-data cases rather than fabricating responses
- **FR3.5:** Support query history and follow-up/contextual questions within a session
- **FR3.6:** Provide response formatting suited to administrative/parliamentary use (concise, factual, citation-backed)
- **FR3.7 (SQL safety):** Generated SQL runs read-only, against an allow-listed set of views scoped to the user's RBAC subsidiary access. Queries are validated (single SELECT statement, no DDL/DML) before execution. The executed SQL is shown to the reviewer.
- **FR3.8 (Parliamentary format):** Provide an answer template for parliamentary questions with Starred/Unstarred question layout (question number, subject, answer text, annexure/table). Past approved replies are indexed as a retrieval corpus so a new question can surface earlier related answers, and the system warns when a new figure differs from a previously approved figure for the same period. Exact format and house style to be confirmed against real samples in Phase 1.
- **FR3.9 (Tables and charts):** When an answer contains a multi-row comparison or time series, return it as a table and, optionally, a chart, with the same citation chain

### Module 4: AI-Assisted Insights & Recommendations Engine

**Purpose:** Convert validated historical and contemporary data into proactive, evidence-backed insights and recommendations for decision-makers — directly addressing the PS's "AI-generated recommendations" requirement.

**Processing Flow:**

```
Validated Historical Data
        ↓
Trend / Pattern Analysis
        ↓
AI-generated Insight
        ↓
Evidence + Source Linkage
        ↓
Recommendation
        ↓
Human Review / Approval
```

**Functional Requirements:**

- **FR4.1:** Continuously analyze validated data (production figures, geological indicators, compliance metrics) for trends, anomalies, and recurring patterns across reporting periods
- **FR4.2:** Generate plain-language insights describing detected patterns (e.g., "Production has decreased for three consecutive reporting periods")
- **FR4.3:** Attach supporting evidence to every insight — the specific historical records/documents that justify the observation
- **FR4.4:** Convert insights into actionable recommendations for planners/policy-makers, clearly labeled as AI-generated and advisory (not a final decision)
- **FR4.5:** Route all recommendations through a human-review/approval step before being included in an official report or response
- **FR4.6:** Allow drill-down from any recommendation to its underlying evidence chain (data → source documents → analysis)
- **FR4.7:** Never present an insight or recommendation without a traceable evidence base — no unsupported claims

**Example Output:**

> "Production has decreased for three consecutive reporting periods. Historical records indicate equipment downtime as a recurring factor."
> Supporting evidence: [linked production logs, maintenance records, source document references]

## 5A. Domain Schema and Validation Rules Catalog

The exact schema is finalized in Phase 1 with real report samples. The catalog below is the working baseline so extraction and validation have something concrete to build against. Items marked **(confirm)** must be checked against official CMPDI/CIL/Coal Controller documents before being treated as fact.

### 5A.1 Organizational scope

Data is scoped by subsidiary. Working list: ECL, BCCL, CCL, NCL, WCL, SECL, MCL, NEC (coal-producing subsidiaries of CIL), and CMPDI (planning/design/consultancy). **(confirm)** the exact list and naming used in source reports.

### 5A.2 Entities to extract

| Entity | Example fields |
|---|---|
| Production record | subsidiary, area/mine, period, coal type/grade, quantity, unit, OB/OCP/UG mode **(confirm)** |
| Despatch / offtake record | subsidiary, period, quantity, unit, consumer sector |
| Reserve/resource estimate | coalfield/block, category (Proved / Indicated / Inferred **(confirm)**), depth range, quantity, unit, as-on date |
| Seam data | seam name/number, thickness, depth, dip, parting, quality parameters |
| Quality parameters | GCV/grade, ash %, moisture %, sulphur %, fixed carbon % **(confirm which are used)** |
| Location | coalfield, block, mine, latitude/longitude or grid reference, coordinate system |
| Survey/borehole reference | borehole ID, survey ID, drilling date, agency |
| Document metadata | document ID, title, issuing office, reference number, date, document type, language |

### 5A.3 Units and conventions

- Coal quantity units in source data can be tonnes, lakh tonnes, or million tonnes (MT). Every value is stored with its original unit **and** a normalized value in one canonical unit (working choice: tonnes). 1 million tonnes = 10 lakh tonnes = 1,000,000 tonnes.
- Reporting period convention: Indian financial year (April–March) vs. calendar year must be recorded per document. A value is never compared across documents until its period basis is known.
- Monthly vs. cumulative-to-date figures must be tagged. A cumulative figure is never treated as a monthly one.
- Grades and reserve categories are stored as controlled vocabularies, not free text.

### 5A.4 Validation rules catalog

| ID | Rule | Type | On failure |
|---|---|---|---|
| V1 | Mandatory fields present for the record type (subsidiary, period, quantity, unit at minimum) | Completeness | Flag, block from official report |
| V2 | Quantity is numeric, non-negative, and within a plausible range for the record type (ranges configurable per subsidiary) | Range | Flag |
| V3 | Unit recognized and convertible to canonical unit | Unit | Flag |
| V4 | Period parses to a valid month/quarter/year and states FY vs. calendar basis | Period | Flag |
| V5 | Sum of area/mine-level production equals the subsidiary total within a tolerance | Arithmetic | Flag with both numbers shown |
| V6 | Sum of subsidiary totals equals the stated CIL total within a tolerance | Arithmetic | Flag |
| V7 | Monthly values for a year sum to the stated annual figure within tolerance | Arithmetic | Flag |
| V8 | Same subsidiary + period + metric across two documents agree; differences above tolerance are flagged | Cross-document | Flag, show both sources |
| V9 | New figure vs. previously approved figure for same period (parliamentary replies, FR3.8) | Cross-document | Warn reviewer |
| V10 | Percentage fields are between 0 and 100; quality parameters within physical bounds | Range | Flag |
| V11 | Coordinates fall within India's plausible bounding box and within the stated coalfield's region where known | Geographic | Flag |
| V12 | Duplicate record detection (same document re-uploaded or same figure in two files) | Deduplication | Merge suggestion to reviewer |
| V13 | Extraction confidence below threshold | Confidence | Route to human review |

Tolerances, ranges, and thresholds live in configuration, not code, so analysts can tune them without a redeploy.

## 6. High-Level System Architecture

### 6.1 Architecture Flow (Textual)

1. **Ingestion Layer** — accepts scanned PDFs, digital documents, spreadsheets, images, archives; also the watched-folder connector (FR1.10)
2. **Extraction Layer** — OCR/document-AI with pre-processing, layout/table analysis, and English/Hindi recognition for scanned sources; direct parsers for digital sources (PDF text layer, DOCX, XLSX/CSV)
3. **Validation & Normalization Layer** — schema validation, rules catalog (§5A.4), unit/period normalization, deduplication, consistency checks, traceability tagging (source document ID + location)
4. **Data Store** — structured database (validated fields) + document store (raw + extracted text + image assets) + vector index (for RAG retrieval) + corrections store (FR1.11)
5. **Application Layer:**
   - Report Generation Engine (Module 1)
   - Word Cloud / Topic Modeling Engine (Module 2)
   - Query & Response Engine — hybrid text-to-SQL + RAG (Module 3)
   - Insights & Recommendation Engine (Module 4)
6. **Human Review / Approval Layer** — reviewer sign-off before any report, answer, or recommendation is treated as official
7. **Presentation Layer** — dashboard/UI for analysts, report export, query interface, topic visualizations, recommendation review queue

Security, auditability, and traceability apply across every layer above — see Section 8.

### 6.2 Architecture Diagram (Textual Representation)

```
Documents: Scanned PDFs, Digital Docs, Spreadsheets, Images, Archives
      (upload via UI/API, or watched-folder drop)
                              ↓
                       Ingestion Layer
                              ↓
                       OCR / Parsing
        (pre-processing, tables, English + Hindi)
                              ↓
                Domain-Specific Extraction
                              ↓
                        Normalization
                              ↓
                  Validation Layer (§5A.4)
                              ↓
        ┌──────────────┬──────────────┬──────────────┐
        ↓               ↓               ↓               ↓
  Module 1:        Module 2:       Module 3:       Module 4:
  Report Gen       Topic Modeling   Hybrid Q&A      AI Insights &
                   + Word Cloud     (SQL + RAG)     Recommendations
        └──────────────┴──────────────┴──────────────┘
                              ↓
                  Human Review / Approval
                              ↓
     Official Outputs: Reports, Answers, Recommendations
                              ↓
          Reviewer corrections → Corrections store (FR1.11)

   [ Traceability + Security + Audit Logging apply across all layers ]
```

### 6.3 Cross-Cutting Principle: Traceability for Every Figure

This principle applies across all modules — reports, query answers, and recommendations alike. No AI-generated number or claim is presented without a full evidence chain:

```
Value
  ↓
Source Document
  ↓
Page / Table / Cell Reference
  ↓
Extraction Confidence Score
  ↓
Validation Status (validated / pending review / flagged)
```

This chain is enforced at the data layer (Validation & Normalization Layer) so that Module 1 (reports), Module 3 (query answers), and Module 4 (recommendations) all inherit it automatically rather than implementing traceability independently. The system must never invent a figure — if a value cannot be traced to this chain, it is flagged as unverified rather than surfaced as fact.

## 7. Technology Stack

Concrete technology choices for the proposed implementation:

| Layer | Technology |
|---|---|
| Frontend | React + Vite |
| Backend | Python + FastAPI |
| Document Processing | PyMuPDF, python-docx, pandas, openpyxl |
| OCR / Layout | PaddleOCR (primary, incl. table layout and Devanagari models), Tesseract (fallback, English + Hindi language packs) |
| Image pre-processing | OpenCV (deskew, denoise, binarization) |
| AI / LLM (on-prem / sensitive data) | Locally hosted open-weight model served via Ollama or vLLM (e.g., a Qwen, Llama, or Mistral family model — final pick by benchmark on the sample set) |
| AI / LLM (demo, public/synthetic data only) | Gemini / OpenAI-compatible LLM API |
| Embeddings | Sentence Transformers (multilingual model so Hindi text is searchable) |
| Vector Search | FAISS |
| Relational Database | PostgreSQL |
| Topic Modeling | BERTopic (primary), TF-IDF / LDA (fallback, FR2.6) |
| Visualization | Plotly |
| Authentication | JWT + Role-Based Access Control (RBAC) |
| Deployment | Docker (containerized services) |

**Rationale:** Every choice above is open-source or API-based, requires no specialized hardware beyond a standard laptop/cloud VM for the demo, and has mature documentation — reducing integration risk within the hackathon timeline. A local LLM needs more RAM/GPU than a cloud API call; the demo can run against the cloud API on public/synthetic data while the on-prem path is shown working on a smaller local model. This stack is a starting proposal; individual components (e.g., LLM provider, OCR engine) can be swapped without changing the architecture.

### 7A. API / Integration Architecture

The platform exposes and consumes a small, clearly bounded set of interfaces. Most are kept conceptual rather than fully built out for the hackathon — the goal is to show integration is *architected for*, not to build production connectors in the hackathon window. The exception is the watched-folder connector (FR1.10), which is built and demoed.

| Interface | Purpose |
|---|---|
| Ingestion API | Accepts document uploads (PDF, DOCX, XLSX, images) from the UI or an external system |
| Watched-folder connector (built) | Polls a configured directory, ingests new files, writes exported reports to an output directory (FR1.10) |
| Extraction/Validation API | Internal service-to-service calls between extraction, normalization, and validation layers |
| Report API | Triggers report generation for a given template/date range; returns exportable file (PDF/DOCX/XLSX) |
| Query API | Accepts a natural-language query, returns a grounded answer with citations (and SQL for structured answers) |
| Recommendation API | Returns current AI-generated insights/recommendations, filterable by status (pending/approved/rejected) |
| Auth API | Login, token issuance/refresh, role resolution (JWT + RBAC) |
| External Integration Points (conceptual) | REST endpoints designed to be consumed by future SAP/ERP or Ministry-side systems — not implemented for the hackathon, but the API layer's stateless, versioned design (`/api/v1/...`) is built to support this without rearchitecting |

All internal services communicate over REST/JSON; the API layer sits between the Application Layer and Presentation Layer described in Section 6, so a future consumer (e.g., an internal CIL portal) could call the same endpoints the dashboard uses.

### 7B. AI Model Configuration & Fallback

The platform is built to be model-agnostic rather than hard-wired to one provider, since LLM/API access can be unreliable during a live demo and must change for production for data-residency reasons.

- **Two deployment profiles, set by configuration:**
  - **Private/on-prem profile (production target):** all LLM, embedding, OCR, and database calls stay inside the private network. Uses the locally hosted open-weight model. No document text or query leaves the network.
  - **Demo profile:** may use a cloud LLM API, but **only on public and synthetic data** (see §11). Confidential CIL data is never sent to an external API under any profile.
- **Primary LLM:** Configured via environment variable — no code change needed to swap providers or move between profiles
- **Fallback path:** If the primary LLM call fails or times out, the system falls back to a secondary configured provider (including the local model) or a cached/offline response for previously-asked demo queries, so a live demo is not dependent on one API being up
- **OCR fallback:** PaddleOCR as primary engine; Tesseract as a local, dependency-light fallback if PaddleOCR fails on a given document type
- **Confidence thresholding:** Any LLM-generated answer or extracted figure below a configured confidence threshold is flagged for human review rather than silently returned (ties directly into the traceability chain in Section 6.3)
- **Prompt/version tracking:** Each AI-generated output stores which model and prompt version produced it, so outputs remain auditable if the underlying model changes later
- **Local model caveat:** Smaller local models are weaker at text-to-SQL and long-context answers than large cloud models. The SQL validator (FR3.7) and citation checks apply to both, and Phase 4 testing (§12) compares the two profiles so the accuracy cost of going on-prem is measured, not guessed.

### 7C. Scalability & Deployment Considerations

- **Modular services:** Each layer in Section 6 (ingestion, extraction, validation, application modules) is a separately deployable Docker service, so individual components can be scaled, replaced, or upgraded independently rather than as one monolith
- **On-premise/private deployment:** Given the sensitivity of geological/mining data, the full stack (PostgreSQL, vector index, backend services, and the local LLM) is designed to run entirely within a private network or on-premise CIL infrastructure. The on-prem profile has no public cloud dependency. The cloud LLM API used in the demo profile is the only external dependency and is disabled in the on-prem profile.
- **Extensibility to new document types/data sources:** New source formats are added by implementing a new parser/extractor plugin against the existing Extraction Layer interface, without changing the Validation, Application, or Presentation layers
- **Horizontal scaling:** Stateless API services (FastAPI) can be scaled behind a load balancer; PostgreSQL and the vector index (FAISS) can be upgraded to managed/clustered equivalents for production load without changing the application layer's interface
- **Multi-subsidiary readiness:** Schema and RBAC design (Section 8) already scope data by subsidiary, so onboarding an additional CIL subsidiary is a configuration step (plus its own rule tolerances in §5A.4), not a redesign

## 8. Security & Data Governance

This is a government reporting system feeding parliamentary and administrative responses — security and governance are treated as first-class requirements, not an afterthought.

### 8.1 Authentication & Authorization

- JWT-based authentication for all user sessions
- Role-Based Access Control (RBAC) with at minimum three roles:
  - **Admin** — full system configuration, user management
  - **Analyst** — document upload, report generation, query access
  - **Reviewer** — approval/rejection of AI-generated reports, answers, and recommendations
- Role-specific document and dataset access (not all users see all subsidiaries' data by default). The structured Q&A path enforces the same scoping (FR3.7).

### 8.2 Data Protection

- Encryption in transit (TLS) for all client-server and service-to-service communication
- Secure storage of uploaded documents (encrypted at rest where deployment environment supports it)
- Controlled, logged access to sensitive documents
- Architecture supports an on-premise/private deployment option for production use, given the sensitivity of geological/mining data (see §7B, §7C)
- No confidential document content is sent to an external LLM API

### 8.3 Auditability

Every significant action is logged along a clear chain:

```
User → Uploaded Document → Extraction Performed → Validation Performed
     → Report / Answer / Recommendation Generated → Reviewer Approved / Rejected
```

This audit trail is what makes the system defensible in a parliamentary/administrative context — any output can be traced back to who did what, and when.

### 8.4 AI Governance

These principles apply across all four modules and tie directly into the traceability chain in Section 6.3:

- AI-extracted figures cannot become official figures without human validation
- Every extracted figure carries source document, page/table reference, and confidence score
- Low-confidence extractions are flagged, never silently accepted
- AI-generated recommendations are explicitly labeled advisory, not decisions
- Human approval is required before any report, answer, or recommendation is treated as official
- Q&A responses always include supporting source citations
- Generated SQL is read-only, validated, and shown to the reviewer

## 10. Competitive Differentiation

A generic document-AI/RAG system typically looks like:

```
Document → Extract Text → Search
```

This project's differentiation is structured, domain-specific, and governance-aware:

```
Document → OCR/Parsing → Domain-Specific Extraction → Validation
  → Source Traceability → Report Generation → Hybrid Q&A (SQL + RAG)
  → Historical Trend Analysis → AI Insights → Human Approval
```

**Key technical differentiators:**

- Source-level traceability for every figure, answer, and recommendation
- Validation gate (explicit rules catalog) before anything becomes an official figure
- Numeric questions answered from validated tables via read-only SQL, not guessed from text chunks
- Purpose-built for government/parliamentary query workflows, not generic enterprise search
- Combines historical and current data analysis in one platform
- Human-in-the-loop approval built into the core workflow, not bolted on
- Private/on-prem profile with a local LLM, so sensitive data never leaves the network
- One integrated platform covering all three PS-mandated outcomes plus recommendations
- AI recommendations are evidence-linked, not free-text generation

## 11. SIH Implementation / Demo Scope

To set clear expectations with judges and avoid questions about confidential CIL data access, the hackathon build's scope is stated explicitly.

**Built and working, demonstrated end-to-end on representative data:**

- All four modules (Report Generation, Word Cloud/Topic Identification, hybrid Q&A, Insights & Recommendations)
- Full ingestion → extraction → validation → output pipeline
- Validation rules catalog (§5A.4) running on the sample data
- RBAC, JWT authentication, and audit logging (basic working implementation)
- Watched-folder ingestion connector and template export (FR1.10)
- Reviewer-correction capture (FR1.11)

**Mocked or conceptual (not built):**

- SAP/ERP and Ministry-side system integration — API endpoints designed and documented only (§7A)
- Production-scale deployment, HA, and hardening
- Full historical archive digitization

**Representative datasets used for validation (not live confidential CIL data):**

- Public Ministry of Coal / CMPDI / Coal Controller's Organisation disclosures
- Synthetic mining/production datasets modeled on realistic patterns

- Mock historical archive samples to demonstrate archival handling

**Explicitly out of scope for the hackathon build:**

- Live confidential/classified CIL data
- Sending any confidential data to a cloud LLM
- Reliable handwritten-record recognition

The platform is complete and end-to-end across the four modules, but it is validated against representative data rather than production CIL systems, which is standard for a time-boxed hackathon build. Where something is mocked, the demo says so.

## 12. Evaluation & Testing Strategy

Rather than asserting accuracy numbers upfront, this section defines what will be measured and how, once the pipeline runs against the representative dataset.

### 12.1 Evaluation dataset

| Slice | Working size | Purpose |
|---|---|---|
| Born-digital PDFs / Word | ~15 documents | Direct-parse accuracy |
| Excel / CSV | ~10 files | Spreadsheet parsing, unit/period handling |
| Scanned PDFs / images (English) | ~8 documents | OCR + table extraction |
| Scanned documents (Hindi or mixed) | ~4 documents | Devanagari OCR |
| Archive-style (old/degraded) | ~5 documents | Degraded-scan path |

Total about 40 documents, with **at least 200 fields manually labeled as ground truth** (value, unit, period, source location). Sizes are working targets; the final counts used are reported with the results. Ground truth is labeled by team members and cross-checked by a second member.

### 12.2 Metrics

| Component | Metric |
|---|---|
| Document Extraction | Field-level extraction accuracy (%), reported per slice (born-digital vs. scanned vs. Hindi vs. archive) |
| OCR | Character/word recognition accuracy on scanned samples (%) |
| Table extraction | Cell-level accuracy (%) on table-bearing pages |
| Report Generation | Correctness of generated figures vs. source documents (% of figures correct) |
| Q&A — structured path | Numeric answer correctness (%) on a fixed question set, plus SQL validity rate |
| Q&A — narrative path | Answer relevance + citation correctness |
| Local vs. cloud LLM | Same question set run on both profiles; accuracy difference reported |
| Validation Layer | Detection rate of deliberately injected inconsistencies (planted errors), and false-flag rate |
| Topic Modeling | Topic coherence score and manual sanity check; method used (BERTopic vs. fallback) |
| System Performance | Query/report response time against §5B targets |
| Automation | % of previously manual workflow steps now automated (steps counted from the baseline in 12.3) |

### 12.3 Manual baseline method (for "% reduction in report preparation time")

1. Pick three report types: monthly production report, geological survey summary, parliamentary Q&A brief.
2. For each, have team members compile the report by hand from the same source documents, with a stopwatch, and record time. Repeat with at least three people and take the median.
3. Time the same report through the platform, **including** the human review/correction step.
4. Reduction % = (manual median − platform median) / manual median.
5. State the caveat plainly: team members are not CMPDI analysts, so this is a proxy baseline. If real analyst timings become available, they replace it.

### 12.4 Reporting rule

All percentage targets in §15 are illustrative placeholders and must be replaced with actual measured results before final submission — no numbers are presented as achieved until verified against the test dataset. Every reported number states its dataset slice and sample size.

## 16. Key Risks & Mitigations

| Risk | Mitigation |
|---|---|
| OCR accuracy on poor-quality scans, tables, and Hindi text | Pre-processing (FR1.2c), table layout analysis (FR1.2a), Devanagari models (FR1.2b); scope demo to a curated scanned sample; prioritize born-digital sources for core accuracy claims; low-confidence pages go to human review |
| Hallucination in Query & Response System | Numeric answers from validated tables via read-only SQL; RAG grounding with citations for narrative; flag low-confidence/insufficient-data cases instead of fabricating |
| Wrong or unsafe generated SQL | Single-SELECT validation, allow-listed views, RBAC scoping, SQL shown to reviewer (FR3.7) |
| Data inconsistency across historical vs. contemporary formats, units, and periods | Normalization layer, unit/period rules, rules catalog (§5A) |
| Sensitive data exposure through cloud LLM | Two profiles (§7B): cloud API only on public/synthetic data; on-prem profile with local model for anything real |
| Local LLM weaker than cloud LLM | Measure the gap in Phase 4; keep validator and citation checks identical across profiles; choose model by benchmark |
| Limited real CIL data access | Use public Ministry of Coal/CMPDI disclosures and synthetic datasets modeled on realistic patterns (see §11); clearly label these as representative, not production data |
| Unverified domain assumptions (grades, reserve categories, period conventions) | Items marked **(confirm)** in §5A are checked against official documents in Phase 1 before use |
| Topic modeling unstable on small corpus | Minimum corpus size and TF-IDF/LDA fallback (FR2.6) |
| LLM/API downtime or rate limits during demo | Fallback model path including local model (see §7B); cache prior query responses for demo reliability |
| Proxy baseline not reflecting real analyst effort | State the caveat (§12.3); replace with real analyst timings if obtainable |
| Implementation complexity across multiple modules in a short window | Modular architecture, fixed technology stack, shared validation layer, day-wise plan (§14.1), prioritizing complete end-to-end functionality |
| Judges questioning production feasibility | Explicit Demo Scope section (11) and Scalability section (7C) separate hackathon build from production path |
